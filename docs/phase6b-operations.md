# Dar Market Phase 6B operations

## Architecture and estimated cost

Start a limited pilot on a Linux x86-64 VPS with 4 vCPUs and 8 GB RAM. Use Compose for Caddy, Next.js, PostgreSQL 18, the PDF renderer and scheduler. Keep media and encrypted database backups with an independent S3-compatible provider. Use a transactional email service. Validate connectivity and regional latency from the target markets before choosing a region and review jurisdiction and data residency with the operator.

The proxy image uses Caddy 2.11.9 for the November security fixes. Resolve the Node 24 and PostgreSQL 18 base tags to reviewed image digests at release time and scan those digests. [Caddy 2.11.9 release](https://github.com/caddyserver/caddy/releases/tag/v2.11.9)

## Environment setup

| Environment | Entry point | Data, secrets and identities |
| --- | --- | --- |
| Development | `npm ci` then `npm run local:dev` | Loopback PostgreSQL and object storage, development keys, local outbox and development fixtures. |
| Native staging equivalent | `npm run local:staging` | Separate PostgreSQL cluster on 55443, S3 fixture on 4579, process-isolated PDF worker, localhost app on 3220, separate keys/admin accounts and local outbox. The native fallback uses HTTP. |
| Container staging equivalent | `npm run ops:staging-env`, build, then `bash scripts/ops/staging-smoke.sh` | `dar_staging`, independent generated credentials, loopback Caddy HTTPS 8443, separate named volumes, fixture buckets and file outbox. The smoke test trusts the fixture CA for its own requests. |
| Production template | `infra/env` and `infra/bootstrap-production.sql` | New `dar_production` cluster, production-only keys and admin accounts, separate media and backup buckets, HTTPS and verified sending domain. |

Use separate hosts or independent projects and networks for real staging and production. Never import fixtures or copy production personal or payment data to staging. Create initial admin accounts with the platform operator and enroll MFA separately per environment. The generator writes once to `.ops/staging`. Preserve those files for the matching fixture volumes. Use `config --quiet` because regular `docker compose config` can print injected secrets.

The application uses separate runtime and identity logins. The pools cap those at 10 and 4 connections. The scheduler uses up to 3 worker connections. PostgreSQL sets login limits of 12, 6, 5 and 3 for runtime, identity, worker and backup respectively. The app checks its restricted role, RLS and ownership before issuing normal queries. The migration owner and initial PostgreSQL admin are isolated from the application. Only the backup role can bypass RLS, for full-cluster table reads within the application DB, with read-only defaults and no application-role membership. Keep its credential in the backup service and rotate it independently. Recalculate connection capacity before adding replicas and preserve direct session semantics for jobs that hold advisory locks.

`0018_operations_queue.sql` adds the RLS-enabled notifications queue and the nullable evidence key ID. `0019_operations_access.sql` adds restricted queue claim and acknowledgement functions, scoped evidence access, job monitoring and audit-chain checks. The runtime roles receive no direct queue access. Existing evidence rows keep the legacy key format. These migrations do not rewrite merchant payment or subscription data. Preserve the additive schema during app rollback once the queue or V2 evidence is in use.

## Release and rollback

1. Run `npm run local:verify`, `npx drizzle-kit check`, both npm audits and CI. On a Docker host, build and smoke-test the staging stack. Review migration SQL, base-image digests, dependency findings and the release manifest. Record previous and candidate image digests and the checksum of the off-server backup. Keep older proof and backup keys available.
2. Require explicit production approval. Under that approval only, copy templates into protected `.ops/production` files and replace placeholders with unique secrets. Use a restrictive firewall, permit 80/443 and restricted administration only, and keep PostgreSQL, object storage and metrics unexposed. Maintain accurate time for TOTP and TLS. The proxy replaces `X-Real-IP` and forwarding headers. A CDN in front requires an explicit trusted-proxy review before changing the IP model.
3. For the first approved cluster, start `db` and run `infra/bootstrap-production.sql` in local interactive `psql` on `dar_production` as `dar_admin`. Use protected password prompts. Enable disk encryption and independent storage credentials. Create the private `ops/readiness` sentinel before booting the app. Use `docker compose --project-name dar-production --env-file .ops/production/compose.env --profile operator run --rm operator` to migrate. On an existing installation, use the existing owner and roles. Take a confirmed backup before migration and keep a maintenance window when a change needs it.
4. Use the same Compose project and reviewed image digests to start the approved app, proxy, PDF and scheduler. Check `/api/health`, `/api/ready`, HTTPS and secure cookies, blocked signup, admin MFA, a synthetic private proof review and the scheduler history. Install the backup timer after verifying the first run. Never expose the Docker socket to an application container.
5. For an application rollback, retain data volumes and the new schema. Switch all service image references back to a release tested against that schema and verify again. The pre-6B app can serve old originals only; an app rollback after new V2 proof uploads requires a compatibility build or read-only billing until roll-forward. For incompatible schemas or data issues, restore a pre-change snapshot into a new isolated database, quantify later writes and reconcile before a separately approved switch. Preserve the current volume for investigation.

CI contains checks and a staging smoke workflow. Production deployment remains manual and approval-gated. There is no repository deployment trigger, production token or public endpoint configured by this phase.

After approval and image verification, an operator can apply the candidate or schema-compatible rollback by pointing the four `DAR_*_IMAGE` values at the corresponding immutable image references. Use the same Compose project for both operations.

```bash
compose=(docker compose --project-name dar-production --env-file .ops/production/compose.env)
"${compose[@]}" --profile operator --profile backup config --quiet
"${compose[@]}" up --no-build --wait -d db app pdf proxy worker
```

The production proof and backups use separate encryption keys. The previous release must retain the full key material required by the current data.

## Backups, storage and recovery

Run `npm run ops:backup` inside the `backup` profile with the daily systemd timer. The script streams `pg_dump -Fc` through AES-256-GCM, uploads ciphertext to `postgres/`, confirms remote size and keeps confirmed copies in the spool for 7 days. Monitor stale or unconfirmed files and disk space. Configure independent object-store lifecycle for 35 days, versioning and immutability, and keep replication and retention under a separate recovery administrator. Backups have a single-upload limit of 5 GB and a 180 s upload deadline. Switch to a reviewed multipart or WAL-based path before approaching either limit. [PostgreSQL dump documentation](https://www.postgresql.org/docs/current/app-pgdump.html)

Target an RPO of 24 hours after a successful daily backup and an RTO of four hours for a small pilot. These are objectives. Daily snapshots provide no point-in-time recovery and a missed backup extends the loss window. Monitor missing success at 26 hours and rehearse recovery monthly. For recovery, provision roles on a separate cluster and an empty `dar_restore_<ticket>` database. Use an isolated encrypted workspace with sufficient scratch space, an independent read credential, `RESTORE_DATABASE_URL`, `RESTORE_CONFIRM`, and the original backup key ID and key ring. Run `node scripts/ops/backup.mjs restore postgres/<artifact>.enc`. Authentication precedes restore, and PostgreSQL restores in a transaction. Verify migrations, table counts, RLS/roles, representative original proof decryption, media links and billing state before selecting a cutover. Roles and provider settings are separate bootstrap inputs. The local rehearsal uses synthetic data and an isolated emulator.

| Storage identity | Permission scope |
| --- | --- |
| App | `GetObject`/`PutObject` for tenant `*/catalog/*.webp` and `*/theme/*.webp`, plus `GetObject` for `ops/readiness`. Signed server requests only. |
| Media worker | `DeleteObject` for the tenant catalog/theme prefixes. PostgreSQL supplies keys through the authorized orphan queue. |
| Backup writer | `PutObject` and the provider permission required for `HeadObject` in the separate backup bucket `postgres/` prefix. Deny deletes. |
| Recovery operator | Time-limited `GetObject` scoped to the approved backup prefix or object, and recovery-only DB access. |

Block public bucket access, ACL changes and broad listing. Restrict provider endpoints and require TLS and encryption at rest. Keep separate credentials by environment and task. Existing tenant media reservations enforce quotas, accepted image bytes are checked and normalized to WebP, and the app serves eligible images through its authorization path. Payment proofs remain behind session, reviewer and MFA checks with `no-store`. Keep object versioning and a separate recovery copy. During recovery, restore object versions referenced by PostgreSQL, verify a sample of keys per tenant, and resume cleanup after validation.

## PDF, email and scheduled jobs

- The app sends eligible PDFs over a private socket to a separate non-root container with no network, dropped capabilities, read-only root, 384 MB RAM and 0.75 CPU. The renderer processes one document at a time, up to 5 MB and 3 pages with a 9-second child deadline. It streams data without disk files. Every accepted page goes into the WebP preview and the authorized encrypted original preserves the complete file. Rejected, overloaded or timed-out renders fail closed. Use local synthetic documents when checking after image or policy changes.
- Configure SPF and DKIM exactly as reported for the sending subdomain, then use aligned DMARC and monitor aggregate reports before increasing enforcement. Disable provider link/open tracking for identity messages. Use provider suppression for hard bounces and complaints, monitor delivery and rejection in its console, and verify the route using sandbox addresses before live enrollment. Operator alerts must contain only operational categories. A signed bounce webhook receiver is not part of this implementation. Identity actions use bounded issuance and expire single-use links. Operational messages use leases, provider idempotency keys, bounded exponential retries and terminal status. The default operational locale is Arabic and can be set to English with `OPS_MAIL_LOCALE=en`.
- The scheduler runs billing (including trial and grace expiry) every 5 minutes, media every 10, reminders every 3, and order retention and audit maintenance daily. It checks missed jobs every 5 minutes. Advisory locks prevent concurrent job runs. For a reviewed manual run, use `docker compose ... run --rm worker node scripts/ops/scheduler.mjs --once <billing|media|orders|notifications|maintenance|inspect>`. The notification worker rechecks current reviewer/owner authorization and verified email before sending. Use only staging credentials for synthetic mail. Check job history under platform operations and scheduler logs for `job_finished`, `worker_missed`, retry and terminal counts. Restarting the scheduler may run jobs immediately. Jobs are designed to tolerate that.

## Secrets and incident response

Keep production secrets in the operator's vault. Supply protected `.ops` files with 0600 mode, and give the PDF process no app, storage or database secrets. Use separate high-entropy values for backups, payment proof encryption, MFA and metrics. Stage proof rotation by adding a new key ID and key to `PAYMENT_PROOF_KEYRING`, then set `PAYMENT_PROOF_ACTIVE_KEY` after all readers have the updated ring. Preserve `PAYMENT_PROOF_KEY` for pre-6B originals and prior versioned keys through evidence and backup retention. Test all key versions on restored copies. Rotate the active backup key using `BACKUP_KEY_ID`/`BACKUP_KEY` and keep prior values in the recovery vault for `BACKUP_KEYRING`. KMS envelope encryption is a future operator option. First verify round-trip and cross-account recovery independently of the failed host.

Sessions use opaque per-session secrets rather than one global signing key. In an incident, revoke affected database sessions using the protected operator and log the decision and scope. Rotate exposed infrastructure credentials and clear affected client sessions. MFA has a separate key with no versioned ring. A compromised MFA key requires controlled recovery and administrator re-enrollment with fresh recovery codes. Use secure cookies via HTTPS, keep the default Next.js security headers, and exclude logs, exports, secrets and fixture inboxes from release artifacts. CI scans tracked history for secrets and redacts reported matches.

Use external uptime checks on `/api/health` and `/api/ready`. Readiness checks the two restricted DB connections, signed storage access and the PDF socket. It checks mail configuration; verify actual delivery separately. Scrape `/api/metrics` on the private app network with `OPS_METRICS_TOKEN`. Collect Caddy latency and HTTP counters from its loopback admin endpoint `/metrics` via a colocated collector. Keep that endpoint private. Forward redacted application, scheduler and backup logs off-host. `DAR_ALERT_WEBHOOK` and `DAR_ALERT_KEY` connect an approved HTTPS destination without raw tokens, emails, order content or request bodies. Configure alerts for two consecutive readiness failures, elevated 5xx/p95, missed jobs, backup age, disk, storage/email/PDF failures, auth limiting and billing review errors. Verify alert receipt end to end before launch.

For an incident, record UTC time and scope, preserve audit/logs and ciphertext, quarantine the affected component, revoke credentials or sessions, then verify recovery on synthetic fixtures before resuming. Export the database audit chain checkpoint to an independent append-only destination. The in-database chain detects changes but a privileged operator could recompute it. Never use a recovery operation to overwrite the sole surviving database or evidence copy.

## Pilot readiness gates

- Verify all images and the full Compose HTTPS smoke on a Linux Docker runner. Confirm the proxy cannot publish PostgreSQL, the renderer has no egress, and readiness returns 503 when dependencies fail.
- Confirm configured private cloud bucket permissions, regional data placement, off-host immutable backup and representative restore under approved credentials. Check recovery capacity and backup retention against local obligations.
- Confirm verified transactional sending, controlled recipient lists, actual delivery and alert routes. Keep public signup disabled and restrict pilot enrolment to approved accounts.
- Confirm current billing and suspension policies, independent manual reconciliation and MFA for reviewers, the legacy store policy from Phase 6A, and named operational owners. No financial data backfill is required by the two Phase 6B migrations.
- Exercise release, rollback, restore and incident handoff with a second operator. Review runtime and build dependency findings and record exceptions before release.

The local load test runs 96 requests with 8 concurrent clients across two synthetic tenants against the production Next.js build. It mixes Arabic storefronts, English product pages and server-priced KWD cart quotes, checks tenant content and `no-store`, and records p50/p95/p99. Regression suites cover concurrent approval, RLS, expiry, suspension, MFA and private proofs. This exercise is a local regression signal. A Phase 6C limited invite-only pilot is appropriate after the gates above and review approval.

- Docker 28.5.2 and Compose 2.40.3 built all five project images. The isolated stack ran PostgreSQL 18.6, Caddy 2.11.9 and Node 24.22.2.
