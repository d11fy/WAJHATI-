# Phase 6A preflight

- Phase 5 baseline verified 20 unit tests, 33 PostgreSQL tests and five Chrome journeys on the existing build.
- The actual runtime role was a member of storefront_app only, with no superuser, BYPASSRLS, CREATEROLE or maintenance membership. Twenty-nine tables had active row security. Runtime had no SELECT on private payment proofs, but could read users.password_hash and insert arbitrary sessions. Move credential and session issuance to a distinct login and keep only token-scoped session lookup and revocation on the runtime connection.
- Phase 5 review checks store conflicts, proof presence, exact amount, currency and transfer reference, a manually verified independent record, and transaction uniqueness. Its store advisory lock and period exclusion constraint prevent concurrent overlapping activation. It lacks recent MFA and a second approver. Preserve the financial function and require fresh MFA and policy authorization at its only runtime entry point.
- Phase 5 uses database time. Trialing ends at trial_end. Pending describes an open request without an effective plan. Paid terms begin only after approval and can queue after the current term. Grace keeps permissions until grace_until; scheduled cancellation skips grace; suspended and expired preserve tenant content. Downgrade applies on the next period boundary and falls back to the basic style. A suspended-by-platform store will be hidden separately from subscription status.
- The 36 stores reported at Phase 5 were restored test fixtures. This audit found 45 legacy rows in the verification database after additional regression fixtures, zero with a verified paid period. The local development database had zero stores and zero billing reviews at this point. There is no production population available to classify. Record a finite 90-day migration window for legacy-only access, without creating or rewriting any payment or subscription records. Preserve approved terms, including historical ones.
- Phase 5 PDF processing limits file size and page count, runs with a stripped environment and composites all accepted pages. It is not an OS sandbox. The preview removes annotation content and original metadata, and large receipts can lose readability. Archive the source privately for new receipts, keep the preview separate, and fail closed outside local development without an isolated renderer. Older receipts retain the existing preview; originals cannot be recovered.
- npm audit reported 12 moderate development dependency findings through esbuild, minimatch and their dependent tooling; zero production dependency findings at baseline. Do not publish a development server.
- Schema migrations in this phase add security records and replace access functions only. No approved amounts, payment proofs, periods, subscriptions or reviews are backfilled or rewritten.

## Migration and rollback

Migrations 0012–0017 add 13 protected tables, enable RLS on users and sessions, and replace the runtime grants for identity and payment review. The existing reviewer list is copied as a reviewer role, with no active MFA enrollment created by migration. A separate transition table records a 90-day cutoff for Phase 5 legacy markers. Sensitive operations recheck the caller inside the lock that coordinates role changes. There are no writes to historical payment amounts, reviews, paid periods or subscriptions.

A local rehearsal restored the Phase 5 archive into an isolated database and seeded one synthetic paid store and one legacy store. Fingerprints of payment requests, reviews, paid periods, and subscriptions matched before and after migration. The paid store retained its active Pro period, and only the legacy fixture received transitional access.

Before rollout, snapshot PostgreSQL, validate restore in a separate instance, and provision the NOLOGIN `storefront_identity` group and its dedicated restricted login. The migration owner needs to install `pgcrypto`; Phase 5 already uses `btree_gist`. Verify that the runtime cannot assume the identity or maintenance role and that the identity login has no runtime or maintenance membership. On an upgraded cluster, revoke any inherited CREATE on the public schema from ordinary roles. Keep the owner connection out of the server process. Roll back application and schema together using a rehearsed plan. If new activity exists, use forward recovery or export/reconcile new audit and billing records before restoring an older snapshot.

## Billing review and evidence

The original Phase 5 transaction still performs independent amount, currency, transfer and proof checks and prevents duplicate transfers and overlapping paid periods. Runtime can execute only the guarded entry point. First approval on a high-risk payment is a distinct audited action and does not create a paid period. The second approval requires a different recently verified reviewer and the same independent record. Initiating a high-risk approval prevents bypass by lowering the threshold later.

The upload stores the preview and encrypted original in one transaction. The original preserves source pages and metadata, is authenticated with AES-GCM bound to the payment ID and media type, and is available only as an audited attachment after fresh reviewer MFA. The preview rasterizes one to three PDF pages as an ordered composite, with a 5 MiB input and output cap. Interactive annotations and metadata may be absent from the preview. Four or more pages are rejected rather than clipped. Historical Phase 5 proofs have no original to recover. The Phase 5 cleanup rule deletes reviewed proof previews after 180 days and cascades to encrypted originals. Unreviewed evidence remains pending an operator decision. PostgreSQL backup volume can increase by up to 5 MiB per accepted proof in addition to previews; protect backups and separately escrow the proof key.

For loopback development only, the PDF renderer uses a bounded child process with stripped environment, a 10-second timeout and at most two concurrent PDF jobs per process. It is not an OS security boundary. Outside that mode, PDF processing fails closed unless an isolated HTTPS renderer is configured. The renderer contract is authenticated POST of a PDF, with an `image/webp` response and `X-Rendered-Pages` of 1–3. The application bounds and decodes the returned WebP. The independent renderer must enforce page counts, memory and process limits, timeouts and denial of access to application disks, credentials and arbitrary network destinations. Provision and test it separately before production. Reviewers should use an isolated original-file viewer.

## Production readiness checklist

- [ ] Restore a backup with the final migrations and exercise rollback. Keep separate backup and key access. The two encryption keys have distinct purposes and require a coordinated rotation/re-enrollment plan.
- [ ] Set the actual HTTPS origin, strict reverse-proxy header stripping, protected runtime/identity/maintenance credentials, and verified mail sender. Send and consume test links before enabling public signup. Live Resend delivery was outside local verification.
- [ ] Provision a renderer behind an OS/container sandbox and authenticate the endpoint. Verify readability and original retrieval with representative long receipts and an isolated reviewer environment.
- [ ] Assign distinct verified reviewer accounts, complete MFA enrollment, test recovery and configure per-currency dual thresholds. Reconcile real funds against independent payment records.
- [ ] Schedule `media:cleanup`, `orders:cleanup` and `billing:expire`. Alert when a run fails or remains unfinished beyond its expected duration. Rerun failed idempotent tasks through the scheduler. The admin job page keeps 90 days of run metadata.
- [ ] Monitor `/api/health` for liveness and `/api/ready` for restricted database connectivity and configuration. Readiness checks configured provider/renderer settings, not upstream delivery or isolation. Configure the optional HTTPS alert hook; test destination behavior. Use external monitoring for stalled workers and provider outages.
- [ ] Configure PostgreSQL and proxy logs to suppress bound query parameters and never persist auth request bodies. Export a periodically anchored audit hash to an independently controlled append-only system. The internal hash chain detects edits without an external anchor only against an attacker who cannot rewrite the chain. Application process compromise can expose both database connection secrets.
- [ ] Review the evidence retention period and backlog, and verify encrypted database backups plus key recovery. Review existing development-only npm advisories and keep toolchain development servers private.

## Phase 6B recommendations

Introduce phishing-resistant WebAuthn for privileged users, external audit anchoring, a separate identity process with independent secret access, key rotation through KMS, and tracked escalation for overdue reconciliation and worker failures. Add a provider-based sandbox validation pipeline and integration tests for production mail delivery, backups and disaster recovery. These are operational readiness items, independent of the storefront Figma workstream.

## Local verification results

The final verification exited successfully. Lint, TypeScript, production build, 23 unit tests, 41 PostgreSQL integration tests and seven Chrome journeys passed. Both health routes returned HTTP 200 with the local configuration, and the three maintenance jobs ran with restricted credentials. Drizzle validated the migration journal. Runtime had active RLS on 44 tables and could neither read password hashes or original proofs, issue sessions, nor call the previous payment approval routine. npm audit reported zero production dependency findings and 12 moderate development dependency findings.
